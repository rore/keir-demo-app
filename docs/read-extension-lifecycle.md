# Review and select task advice

Choose **Customizations** from Daymark's normal navigation to see saved items and their statuses, begin a nonmutating conversation, or open an existing item. **New customization** starts that conversation; **Create from a description** remains visibly disabled as **To be implemented**. Task advice is the working discovery/setup starting point. It offers two prepared rules: Pending or Needs attention for open tasks across the person's projects; both show Done for completed tasks. These are existing compiled read-only programs. Studio also has an optional manual developer qualification tool for authored source; it does not call AI or create follow-up tasks. See [authored extension drafts](authored-extension-drafts.md) for that path.

1. Choose a proposed rule. Your current advice stays in use.
2. Choose **Try on sample tasks**. The server runs six actual bounded simulations and saves immutable evidence. Compare independently authored expected results with actual results for open, completed, missing, business-denied, host-denied and transient-read cases.
3. Review the exact proposal and sample evidence, then explicitly choose **Approve this advice**. Approval alone leaves current advice unchanged.
4. Choose **Use this advice for me**, return to Tasks, open a saved task and check live advice. The contextual **Manage task advice** shortcut opens this same Studio and returns to its invoking control with unsaved title/notes retained; the check reads saved task status.
5. Open **Details and recovery → Manage saved advice** for **Turn off my advice** or an exact previously used choice to restore. Inspect its provenance and confirm. Neither operation changes native tasks or another person's choice.

The review panel starts closed. Open it with **View proposal**, **Latest run**, **Approved run** or **Manage**; close it with **Back to conversation**. Simulation shows its case count without opening results. Approval remains tied to its exact evidence when a newer run becomes latest; approving that newer run explicitly updates the binding. **Proposed** and **Approved** appear in the status summary outside the transcript, alongside In use, Off or Unavailable. Saved runs, selection history, provenance, technical identities, ID lookup and reload are grouped under management. Wide screens allow workspace resizing; phone-sized screens use a full-workspace view. View changes retain reading position, input, width and focus. New replies do not move someone reading earlier conversation.

Typed assent can open review but never approves or activates a rule. A different proposal invalidates an old activation request even when the active generation is unchanged. Historical sample runs remain available for inspection; they cannot approve a different revision. Failed checks never become a default classification. Conflicts and uncertain mutation responses reload saved state before retry.

## Evidence API meanings

The existing owner-scoped lifecycle state includes nullable `approvedEvidenceId`: the validated saved approval proof for the current eligible customer draft. It is independent of `evidence`, which describes the latest run, and is null without an eligible customer approval, including operator-only choices. Approving A then running B retains A as the approved proof after re-entry; only explicitly approving B changes that binding. Both proofs open through the existing owner-scoped evidence lookup. This readback adds no endpoint, migration or mutation authority.

Each saved suite returns `reports[]` with a server-held independent `expected` annotation and an actual simulator `report`. These fields have different types:

| Field | Meaning |
| --- | --- |
| `expected.classification` | Expected native outcome category: `COMPLETED`, `BUSINESS_REJECTION`, `FAILED` or `LIMIT_EXCEEDED`; never a display receipt status. |
| `expected.code` | On `COMPLETED`, the expected advisory value (`PENDING`, `NEEDS_ATTENTION` or `DONE`). On rejection/failure, the expected original native diagnostic code. This compact scenario annotation is not itself a consumer receipt. |
| `report.native` | Actual bounded native summary from the simulator. Domain rejection codes are redacted to `NATIVE_ERROR`; the original codes are compared privately by the simulator. |
| `report.consumption` | Actual safe receipt: `{status:"DISPLAYED",code:"PENDING"}` (or another allowed advisory code), or `{status:"NOT_DISPLAYED"}`. Native outcome categories never appear in `status`. |

The independently authored case bytes separately pin `expect.outcome` and `expect.consumption`. For a successful case, the expected safe receipt is `DISPLAYED` with the expected advisory code; every rejection/failure case expects `NOT_DISPLAYED` without a code. The server validates actual `report.consumption` against that exact expected receipt, as well as native outcome, complete ordered suite membership and dependency identities. The canvas summarizes expected/actual displayed advice in everyday terms; each row's Technical run details retains the exact expected annotation and actual native/consumption/mismatch fields. It never compares a native category to a receipt status.

The state DTO's `approved` boolean only controls presentation. Approval rechecks server-held owner, exact current draft/revision/version and complete eligible evidence in its committing transaction. Activation rechecks the current draft/version, eligible approval/evidence and expected selection generation before committing. Neither a client boolean nor a rendered PASS authorizes activation. Both curated rules read the saved task status; there is no customer project filter or follow-up creation control.

## Authority and persistence

SQLite schema 3 holds owner-scoped immutable revision identities, authored source/artifact and optional exact case strings, suite evidence, approvals, current draft/version, selection generation and transition history. Schema 1 and 2 databases upgrade additively. The server owns model/artifact/source/compiler/environment/package/adapter/consumer pins and suite/fixture/case identities. A browser submits source or raw case strings plus exact revision IDs and expected versions; it cannot supply owner, artifact, pins, PASS claims or authority overrides. Every approval records its actual owner/approver and exact evidence reference.

The packaged files named `maya` and `leo` are curated template material, not owners. Any demo person can select either through their own records. Maya initially has Pending, Leo Needs attention and Sam no selection. The one-time version-1 upgrade records existing defaults as operator-provided starting choices with actual activation history; it creates no customer approval or simulation evidence. Disabled selections stay disabled after restart. Missing or invalid dependencies never silently reseed defaults.

Advice captures one revision/generation and retains its exact prepared dependencies. Current session, approval/dependencies, ownership and generation are checked before native dispatch and consumption. An away-and-back change still invalidates the old generation. A client epoch advances before each selection mutation, preventing an already-produced late HTTP success or failure from restoring old advice. User changes discard the old workspace, including Studio state; they do not adopt a previous person's responses.

The local server, packaged assets and SQLite file are trusted against direct operating-system replacement. Hashes prove byte identity, not approval authority. This does not protect against a malicious database/server owner and does not provide production identity management. Synthetic simulation does not certify real adapters or all future tasks.

## Limits and recovery

- Prepared advice retains its six cases. Authored suites contain 1–8 cases, each at most 64 KiB and at most 128 KiB together. One simulation per owner and two globally may run; excess work returns 429 without queueing. Slots remain held until settlement.
- Each owner may retain 32 authored revisions, including source-only drafts and suite-bearing copies. Old revisions are not silently deleted. Live advice retains the eight-invocation ceiling and one-second checked deadline; prepared executable entries use an LRU capped at 16. The compiler wrapper uses one active job without a queue, a 10-second deadline and a 256 MiB Java heap setting. These are process controls, not an OS sandbox or hard whole-process memory limit; exact package and qualified Java metadata are recorded in `vendor/compiler-provenance.json`.
- Native simulator case/report limits apply. Lifecycle responses are at most 256 KiB. History/evidence metadata pages contain at most 20 rows; complete evidence is fetched by exact owner-scoped ID. Oversize evidence is rejected, never truncated into eligibility.
- Cancellation stops the request and cannot undo a commit already completed. After an interrupted compile, reload saved state before retrying; the new revision may already exist. The UI does not automatically repeat compilation. Restart requires sign-in while lifecycle selections/evidence persist.

All new database operations use synchronous transactions without awaits. Reset verifies lifecycle rows, including authored bytes, in its recoverable backup before deleting them in dependency order. When upgrading an existing local installation, stop its owning app and retain a recoverable database backup before a deliberate restart. Startup transactionally upgrades schema 1 through 2 to 3, or schema 2 to 3; failed upgrades leave prior data intact. Do not delete or reset a database to resolve an unsupported version. Automated development verification uses synthetic databases; a user preview migration is a separate action for its owner.

## Verification and package

The app consumes the independently packed runtime at the exact source revision in `vendor/provenance.json`. Archive/lock SHA-512 and all eight installed file identities are checked, including the root runtime and `@keir/runtime-node/read-simulation` export. Existing prepared source/artifact/model pins are unchanged; neither Java nor a sibling core checkout is required for app startup or prepared advice. Authored compilation is optional and requires its pinned compiler package and Java 21.

`npm test` includes migration/reopen/reset/backup, prepared six-case simulation, actual packaged compiler/process bounds, third/zero/repeated-call source programs, authored API boundary/version/evidence checks, stale/foreign/forged evidence, explicit approval, transactional generation conflicts, selection versus in-flight reads and existing native regressions. `npm run test:e2e` covers actual Studio/native authored journeys, cancellation/readback, late responses, uncertain activation readback, narrow layout and restart. Browser installation remains project-local and separate from warm execution. API tests also use a synthetic compiler fixture to isolate authority/version boundaries; actual-JAR tests qualify real compilation separately. These tests do not claim AI, effects or production authentication.
