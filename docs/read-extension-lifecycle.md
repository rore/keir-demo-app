# Review and select task advice

Choose **Customizations** from Daymark's normal navigation to start a new conversation or reopen a named saved item. The assistant discovers your intent against the actual host contract. Today's executable support is read-only task advice: Pending, Needs attention or Done. It cannot create tasks or run background automation. Tool authors learning Keir can use the [core manual authoring guide](https://github.com/rore/keir-core/blob/main/docs/manual-authoring.md).

1. Choose **New customization** and describe your goal. It starts empty; opening or typing creates nothing. The first accepted message saves a separate item. Existing advice keeps running.
2. Agree on what should happen in recognizable situations. The assistant compiles the supported change and checks synthetic examples with Keir, explaining any disagreement with the wanted results. The labeled guided example follows a scripted conversation without AI calls.
3. Read the checked behavior in chat. Open a named example when useful; it shows what you wanted and what actually happened. Choose **Approve this change** when eligible results match your intent. Approval alone leaves current advice unchanged.
4. Separately turn on the change, or explicitly switch from the named customization already in use. The previous item stays saved. Return to Tasks and choose **Check task advice** on a saved task. **Manage task advice** returns to Studio while preserving unsaved task title/notes.
5. Use secondary History and management controls to inspect earlier work, turn advice off or restore an eligible previously used choice. These actions never edit native tasks or another person's customization.

Examples start closed and open from a specific exchange. Closing restores that exchange, reading position, focus and unsent text. A newer reply never replaces an example being read. Wide screens allow workspace resizing; phone-sized screens use a full-workspace view. One current decision stays in the conversation; there is no separate approval workflow inside the example. Approval remains tied to its exact evidence when a newer run becomes latest; explicitly reviewing and approving the newer run updates that binding. History and technical inspection retain original source, compiled artifact and saved proof without granting approval or activation of another draft.

New AI-created items start as **Untitled customization**. **Rename** beside the saved name opens an optional name field with Save and Cancel; Enter saves and Escape cancels. Existing names stay unchanged until their owner renames them. Renaming changes display metadata only, preserving the item, revisions, evidence, approval and active selection. When untitled items share a name, a short excerpt of each proven original request helps distinguish them; the excerpt does not promise that the request is supported.

Typed assent can open review but never approves or activates a rule. A different proposal invalidates an old activation request even when the active generation is unchanged. Historical sample runs remain available for inspection; they cannot approve a different revision. Failed checks never become a default classification. Conflicts and uncertain mutation responses reload saved state before retry.

## Evidence API meanings

The existing owner-scoped lifecycle state includes nullable `approvedEvidenceId`: the validated saved approval proof for the current eligible customer draft. It is independent of `evidence`, which describes the latest run, and is null without an eligible customer approval, including operator-only choices. Approving A then running B retains A as the approved proof after re-entry; only explicitly approving B changes that binding. Both proofs open through the existing owner-scoped evidence lookup. This readback adds no endpoint, migration or mutation authority.

Each saved suite returns `reports[]` with a server-held independent `expected` annotation and an actual simulator `report`. These fields have different types:

| Field | Meaning |
| --- | --- |
| `expected.classification` | Expected native outcome category: `COMPLETED`, `BUSINESS_REJECTION`, `FAILED` or `LIMIT_EXCEEDED`; never a display receipt status. |
| `expected.code` | On `COMPLETED`, the expected advisory value (`PENDING`, `NEEDS_ATTENTION` or `DONE`). On rejection/failure, the expected original native diagnostic code. This compact scenario annotation is not itself a consumer receipt. |
| `report.native` | Actual bounded native summary from the simulator. Domain rejection codes are redacted to `NATIVE_ERROR`; the original codes are compared privately by the simulator. |
| `report.consumption` | Actual safe receipt: `{status:"DISPLAYED",code:"PENDING"}` (or another allowed advisory code), or `{status:"NOT_DISPLAYED"}`. Native outcome categories never appear in `status`. |

The independently authored case bytes separately pin `expect.outcome` and `expect.consumption`. For a successful case, the expected safe receipt is `DISPLAYED` with the expected advisory code; every rejection/failure case expects `NOT_DISPLAYED` without a code. The server validates actual `report.consumption` against that exact expected receipt, as well as native outcome, complete ordered suite membership and dependency identities. The canvas summarizes expected/actual displayed advice in everyday terms and prefers an unfinished-task example before a completed-task fallback. Its **Details** disclosure groups Technical run details, example limits, saved identity and the exact report, retaining every expected annotation and actual native/consumption/mismatch field. The visible “Example only — your tasks were not changed” note distinguishes checks from real task effects. It never compares a native category to a receipt status.

`POST /api/extensions/:extensionId/rename` accepts exactly `name` and `expectedName` under the current owner/session. The new name must contain 1–80 Unicode code points after trimming and cannot contain NUL. A transactional comparison checks the exact saved `expectedName` before any update or no-op; stale names return 409 and foreign items return 404. Legacy names remain readable for that comparison. The collection's optional `requestExcerpt` contains at most 160 code points from the uniquely linked original creation request; uncertain linkage omits it. This metadata does not enter provider discovery or confer mutation authority.

`POST /api/extensions/:extensionId/delete` accepts exactly `expectedName`, `draftVersion` and selection `generation` from the confirmation snapshot. It checks the exact owner/name/versions and rejects stale confirmation with 409. Running, cancelling or still-settling authoring for this item returns `409 CUSTOMIZATION_BUSY`: open the discussion, use Stop and wait for settlement before confirming again. Cancel sends no mutation. Deleting the selected item uses the existing disable transition in the same transaction; deleting another item leaves the selected revision and generation unchanged. The response is the stable `{extensionId,deletedAt}` receipt; repeating an owner-scoped deletion returns it without another transition, even with obsolete version fences. Refresh the current list and selection separately.

Deletion removes the item and its linked discussions from normal lists and makes direct item, source, proof, history and restore links unavailable. It retains item identity, revisions, approvals, history, conversations, operation receipts, dispatch records and all reserved or unknown spending. Deleted rows remain valid pagination anchors. Creation and turn receipt replay or recovery returns only `410 CUSTOMIZATION_DELETED`, without recompiling, dispatching or creating a replacement; a mismatched operation still conflicts. The browser clears only the matching pending request on this terminal result. A new explicit creation with a new operation identity is allowed. Late preparation or checks cannot commit to a deleted item, and an in-flight advice read cannot display after selected deletion.

Schema 7 adds nullable nonnegative `extensions.deleted_at` without rebuilding or deleting existing records. Fresh databases and supported upgrades use the same schema; verified reset backups include deletion metadata. Rolling back the application after migration requires its matching pre-upgrade database backup. Deletion offers no undelete or physical audit purge.

The state DTO's `approved` boolean only controls presentation. Approval rechecks server-held owner, exact current draft/revision/version and complete eligible evidence in its committing transaction. Activation rechecks the current draft/version, eligible approval/evidence and expected selection generation before committing. Neither a client boolean nor a rendered PASS authorizes activation. Both curated rules read the saved task status; there is no customer project filter or follow-up creation control.

## Authority and persistence

SQLite schema 5 gives each saved customization an owner-scoped identity and its own versioned draft, immutable revisions and conversations. A new conversation stays unbound to a hook until the host validates compatible source; the sole current hook is not assumed to be the user's intent. Revision bytes, evidence, approvals, selection generation and history remain server-held. The migration preserves existing records and leaves ambiguous old discussions readable without guessing an item link. The server owns model/artifact/source/compiler/environment/package/adapter/consumer pins and suite/fixture/case identities. Browser mutations name the exact item, revision and expected version; they cannot supply owner, artifact, pins, PASS claims or authority overrides. Every approval records its actual owner/approver and exact evidence reference.

The packaged files named `maya` and `leo` are curated template material, not owners. Any demo person can select either through their own records. Maya initially has Pending, Leo Needs attention and Sam no selection. The one-time version-1 upgrade records existing defaults as operator-provided starting choices with actual activation history; it creates no customer approval or simulation evidence. Disabled selections stay disabled after restart. Missing or invalid dependencies never silently reseed defaults.

Advice captures one revision/generation and retains its exact prepared dependencies. Current session, approval/dependencies, ownership and generation are checked before native dispatch and consumption. An away-and-back change still invalidates the old generation. A client epoch advances before each selection mutation, preventing an already-produced late HTTP success or failure from restoring old advice. User changes discard the old workspace, including Studio state; they do not adopt a previous person's responses.

The local server, packaged assets and SQLite file are trusted against direct operating-system replacement. Hashes prove byte identity, not approval authority. This does not protect against a malicious database/server owner and does not provide production identity management. Synthetic simulation does not certify real adapters or all future tasks.

## Limits and recovery

- Prepared advice retains its six cases. Authored suites contain 1–8 cases, each at most 64 KiB and at most 128 KiB together. One simulation per owner and two globally may run; excess work returns 429 without queueing. Slots remain held until settlement.
- Each owner may retain 32 authored revisions, including source-only drafts and suite-bearing copies. Old revisions are not silently deleted. Live advice retains the eight-invocation ceiling and one-second checked deadline; prepared executable entries use an LRU capped at 16. The compiler wrapper uses one active job without a queue, a 10-second deadline and a 256 MiB Java heap setting. These are process controls, not an OS sandbox or hard whole-process memory limit; exact package and qualified Java metadata are recorded in `vendor/compiler-provenance.json`.
- Native simulator case/report limits apply. Lifecycle responses are at most 256 KiB. History/evidence metadata pages contain at most 20 rows; complete evidence is fetched by exact owner-scoped ID. Oversize evidence is rejected, never truncated into eligibility.
- Cancellation stops the request and cannot undo a commit already completed. After an interrupted compile, reload saved state before retrying; the new revision may already exist. The UI does not automatically repeat compilation. Restart requires sign-in while lifecycle selections/evidence persist.

All new database operations use synchronous transactions without awaits. Reset verifies lifecycle rows, including authored bytes, in its recoverable backup before deleting them in dependency order. When upgrading an existing local installation, stop its owning app and retain a recoverable database backup before a deliberate restart. Startup upgrades supported earlier schemas transactionally; failed upgrades preserve prior data and version. A version-5 database cannot be opened with the old app: rollback requires the matching pre-upgrade database backup and app source. Do not delete or reset a database to resolve an unsupported version. Automated development verification uses synthetic databases; a user preview migration is a separate action for its owner.

## Verification and package

The app consumes the independently packed runtime at the exact source revision in `vendor/provenance.json`. Archive/lock SHA-512 and all eight installed file identities are checked, including the root runtime and `@keir/runtime-node/read-simulation` export. Existing prepared source/artifact/model pins are unchanged; neither Java nor a sibling core checkout is required for app startup or prepared advice. Authored compilation is optional and requires its pinned compiler package and Java 21.

`npm test` includes migration/reopen/reset/backup, prepared six-case simulation, actual packaged compiler/process bounds, third/zero/repeated-call source programs, authored API boundary/version/evidence checks, stale/foreign/forged evidence, explicit approval, transactional generation conflicts, selection versus in-flight reads and existing native regressions. `npm run test:e2e` covers actual Studio/native authored journeys, cancellation/readback, late responses, uncertain activation readback, narrow layout and restart. Browser installation remains project-local and separate from warm execution. API tests also use a synthetic compiler fixture to isolate authority/version boundaries; actual-JAR tests qualify real compilation separately. These tests do not claim AI, effects or production authentication.
